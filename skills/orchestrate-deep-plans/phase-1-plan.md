# Phase 1 — Plan the active milestone

1. **Pick the milestone:**
   - A new feature: file it under the epic whose theme it extends, or start a new epic when none fits, and say in one line where it went. A new epic gets its milestones from the cut ([milestone-cut.md](milestone-cut.md)), signed off before any is planned. No `podium.json` yet → register the run and switch its sync on (SKILL.md, `podium`), then write `project` (`title`, `summary`), that epic (`id` as a slug, `title`, one-line `summary`), `needsYou: null`; record the dispatcher (SKILL.md, Dispatcher). Add a milestone (next free id) of the feature's title, `status: "working"`, `phase: "recon"`, empty `stories` and `artifacts`, claim it (SKILL.md, _owner_) and point `active` at it. Start the Podium (SKILL.md, Podium) and give the user the link.
   - `REQUEST plan <id>`, or `/orchestrate-deep-plans <id>`: claim it first (SKILL.md, _owner_). Then another milestone is `working` → **grill it now**, so it is ready when that one lands: put its open questions to the user (the grill of deep-plan's Phase 0, against its brief), write the answers into its brief, `podium set milestone:<id> grilled=now --event grilled note=<what was settled>`, and tell the user it is ready to plan once the active one lands, from its Plan button or by naming it. A `REQUEST plan` for a `parked` or `dropped` milestone → it stays put until the user confirms (naming it in `/orchestrate-deep-plans <id>` is that confirmation): set `needsYou: {reason: "<id> was <status>: <its note's reason>. Unpark and plan it?"}`, append a `request` event, and ask in `AskUserQuestion` when available; while unavailable it waits for `HUMAN available` (unparking is never an assumption). Otherwise set `active` to it, its `status: "working"`, `phase: "recon"`, and append a `planned` event.
2. **Run `/deep-plan`** for the active milestone: its brief when one exists (a `draft` brief → grill its `open` questions first; a `grilled` milestone's answers stand, so go on to the brief's sign-off), otherwise the feature description. deep-plan sees `podium.json`, keeps the milestone's `phase`, `artifacts` and the epic's `needsYou` current at every checkpoint and gate, and returns here after its Phase 2 checkpoint. When deep-plan reaches a context reset, it returns here at that checkpoint: continue in a fresh subagent (Hand-off below), never by asking the user to `/clear`.
3. Set the milestone's `branch` to the feature branch speckit created, and its `spec` to the speckit folder.

**Hand-off.** A fresh `Agent` subagent runs the rest of planning from disk, so the next phases start with a clean context and only the hand-over and its reply land here. `podium handoff <id> plan` writes its prompt from the run's state and prints `PROMPT <file> model=<model>`: start `Agent` (general-purpose) with `run_in_background: true`, that model, and the file's text as the prompt. The prompt resumes `/deep-plan` from the milestone's ledger (`.deep-plan/state.md` in the worktree of its branch), gives the user's mode now and what to do with a question (available or mobile → return it with 2–4 options, unavailable → an assumption), starts no background agent, and returns at the Phase 2 checkpoint, the next context reset or a question, in at most 8 lines.

A returned question → ask the user, then continue the same subagent with `SendMessage` and the answer. Background work it names → run it as your own background subagent and pass its result on the same way. Another reset → a new fresh subagent. `TOO BIG <milestone>: <why>` → re-cut that milestone ([milestone-cut.md](milestone-cut.md)) and plan nothing until its sign-off. `OPEN DECISION <question>: affects <milestones>` → `podium decision add` it on the epic, work it ([milestone-cut.md](milestone-cut.md), Epic decisions), then continue the same subagent with `SendMessage` and the outcome. The Phase 2 checkpoint → step 3.

**Planning ahead.** The user asks to plan later milestones while one builds → claim each (SKILL.md, _owner_), then one background subagent per milestone runs `/deep-plan` through its Phase 2 checkpoint, documents only, in its own worktree on its own planning branch (`../<repo>-plan-<id>` on `plan/<id>-<slug>` off the base), so each keeps its own ledger and checkpoint commits: start each as the Hand-off does, from `podium handoff <id> ahead`. It reads the user's mode with `podium --dir <main checkout>/.deep-plan human` and writes nothing else there. The milestone keeps its `status`; record its `phase` and `artifacts` from each reply, since you stay the only writer of `podium.json`. Its prompt has each **shared number**, a new value from a sequence the whole project draws from (type and slot ids, enum codes, edit groups, migration numbers, ports), go in as a placeholder `«<kind>:<milestone>:<n>»`, listed in the reply with its branch, because the other planners are picking at the same time. As each plan returns, give its placeholders the next free values, commit them into its files on its branch, and add them under `Reservations` in the main ledger, which every later planner and story reads first. When the milestone becomes active, rebase its planning branch onto the base, remove the worktree and continue planning on that branch. Built beside the active milestone instead, it keeps that worktree (SKILL.md, Running two milestones at once).

**Waiting.** Planning concludes the milestone is better done after another that deps don't cover → record `waitsFor` and raise it once (SKILL.md, Waiting for another milestone) before the hand-back.

Done when the ledger names Phase 3, the milestone's `spec.md` and `tasks.md` are on disk, and its `branch` is set.
